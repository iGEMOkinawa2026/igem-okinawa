## 1. CMS とは何か

**CMS（Content Management System）** は、ブラウザ上のフォームに入力するだけで、プログラムのコードを触らずにサイトの文章や画像を更新できる仕組みです。

このサイトでは **Pages CMS**（<https://pagescms.org/>）というサービスを使っています。「Save」を押すと、その内容がすぐにサイトの元データとして保存され、数分後には公開されます。

### このCMSの特徴

- 変更した内容はすべて記録として残ります。間違えても元に戻すことができます
- 専用のデータベースを使っていないので、システム障害でデータが消える心配が少ないです

### 注意点

- 保存すると即座に本番へ反映されます（下書きやプレビューの仕組みはありません → [10章](#10-落とし穴と既知の問題)参照）
- 編集には GitHub アカウントが必要です

## 2. 用語集

| 用語 | 意味 |
| :---- | :---- |
| **コレクション** | 同じ種類のコンテンツのまとまり（例: News, Team Members） |
| **エントリ** | コレクションの中の1件のデータ（記事1件、メンバー1人など） |
| **スラッグ (slug)** | ページのURL（アドレス）の末尾に使う、半角英数字とハイフンだけの文字列 |
| **ビルド** | 入力された内容から、実際に公開するページを作る処理。ここでエラーになると公開が止まります |

## 4. CMS へのログイン

1. <https://app.pagescms.org> を開く
2. **Sign in with GitHub** をクリック
3. GitHub アカウントでログイン
4. 初回は組織 iGEMOkinawa2026 へのアクセス許可を求められる → 許可（組織オーナーの承認が必要な場合があります）
5. リポジトリ一覧から **iGEMOkinawa2026/igem-okinawa** を選択
6. ブランチは **main** を選択（＝本番。保存すると公開されます）

左サイドバーに3章の表のメニューが並びます。

### 編集できる人を増やしたい場合

これは CMS 側ではなく **GitHub 側**の操作です。

1. GitHub で iGEMOkinawa2026 organization にそのアカウントを招待
2. igem-okinawa リポジトリへの **Write 権限**を付与
3. 本人が app.pagescms.org に GitHub ログインすれば編集可能になります

「Team Members にメンバーを追加」は**サイトのチーム紹介ページに人物カードを増やす**ことであり、編集権限とは無関係です。混同しないよう注意してください。

## 5. 共通の操作フロー

どのコレクションでも流れは同じです。

1. 左サイドバーからコレクションを選ぶ
2. 新規なら「+ Add」／既存を直すなら一覧から選択
3. フォームに入力
4. 「Save」をクリック
5. 数分待つ（内容がサイトに反映されるまで少し時間がかかります）
6. サイトを再読み込みして確認

**Save = 本番公開**です。押す前に内容を確認してください。（間違えても元に戻せます。慌てず開発者に連絡してください。）

**削除**は、一覧でエントリを選び「Delete」。これも即座に反映されます。

## 6. コレクション別ガイド

### 6-1. News Articles（ニュース記事）

**英語版と日本語版は別々の記事**として作ります。1つの記事に両言語を入れる形式ではありません（他のコレクションとはここが違います）。

- 英語 → News Articles (English) → /news/{slug} に公開
- 日本語 → News Articles (Japanese) → /ja/news/{slug} に公開

#### 入力項目

| CMS の項目 | 必須 | 説明 |
| :---- | :---- | :---- |
| 記事タイトル | ○ | 記事の見出し |
| 公開日 | ○ | 一覧カードと詳細ページの先頭に表示され、**並び順（新しい順）にも使われる**。予約投稿ではない |
| 短い説明 | ○ | 一覧カードと詳細ページ冒頭に表示 |
| 言語 | ○ | 選択肢はそのコレクションの言語1つだけ（触る必要はありません。下記参照） |
| 公開する | ○ | オフにするとページごと非公開になる |
| URLスラッグ | – | そのまま URL になる（下記参照） |
| カテゴリー | – | 一覧カードと詳細ページ上部にラベル表示 |
| アイキャッチ画像 | – | 一覧カードのサムネイルと、詳細ページの本文冒頭の大きな画像 |
| タグ | – | 複数指定可。表示位置は下記 |
| 本文 | – | Markdown で記述（[9章](#9-markdown-記法早見表)参照） |

> **「言語」欄について**
> News Articles (Japanese) では選択肢が「Japanese」だけ、News Articles (English) では「English」だけです。
> 初期値のまま触らなければ問題ありません。取り違えることはできない作りになっています。

#### 詳細ページでの表示順

上から順に、こう並びます。**タグは記事の冒頭側**にあり、本文の下ではありません。

```
公開日
カテゴリー
記事タイトル
短い説明
タグ（ピル型・中央揃え）
アイキャッチ画像
本文
```

#### URL がどう決まるか（重要）

**「URLスラッグ」欄に入力した文字が、そのままページの URL になります。**

例えば「URLスラッグ」に `science-week-guide` と入力すると、公開後のページは `/ja/news/science-week-guide` という URL になります。

##### スラッグのルール

| ルール | 説明 |
| :---- | :---- |
| 使える文字 | 半角小文字の英数字とハイフンのみ |
| 英語版と日本語版 | 同じスラッグを使ってOK（別々のフォルダに保存されるので問題ありません） |
| 同じ言語の中 | 重複禁止（同じ言語で同じスラッグは使えません） |
| 公開後の変更 | スラッグを変えると URL も変わり、それまでのリンクが切れます。原則変えないこと |

#### カテゴリー・タグ一覧

「カテゴリー」（1記事に1つ）と「タグ」（複数可）は**どちらも自由入力**で、選択肢はあらかじめ決まっていません。現在の記事で実際に使われているのは以下だけです。

| 種別 | 値 | 使用箇所 |
| :---- | :---- | :---- |
| カテゴリー | Support | science-week-fundraising-guide（EN / JA 両方） |
| タグ | Donation | 同上 |
| タグ | Support | 同上 |

##### 運用上の注意

- **表記ゆれに注意。** チェック機能がないため「Support」「support」「サポート」はすべて別のタグとして扱われます。新しいタグを増やす前に、この表と既存記事を確認してください
- 日本語記事でも**英語表記で統一**されています（現状の慣例）
- タグ・カテゴリーは**ラベルとして表示されるだけ**です。クリックできず、絞り込み機能もありません
- カテゴリーは強調色の大文字で表示され、タグはピル型で並びます

#### 記事を書く手順（日本語記事の例）

1. News Articles (Japanese) を開く → **+ Add**
2. 「記事タイトル」「公開日」「短い説明」を入力（必須）
3. 「URLスラッグ」に半角英字で識別子を入力（例: `science-week-guide`）
4. 「言語」は ja のまま、「公開する」はオン
5. 必要なら「カテゴリー」「アイキャッチ画像」「タグ」
6. 「本文」を Markdown で記述（[9章](#9-markdown-記法早見表)参照）
7. **Save**
8. 数分後に `/ja/news/science-week-guide` で公開される
9. 英語版も同様に News Articles (English) で作成

### 6-2. Team Members（チームメンバー）

/team と /ja/team に並ぶ**人物カード**の情報です。1人につき1件登録します。

登録した内容がそのまま並びます。したがって：

- 新しく登録する → カードが1枚増える
- 「Is Leader?」をオン → 上部の **Leadership** セクションに入る
- 「Is Leader?」をオフ → 下部の **Members** セクションに入る
- 「Sort Order」の数値が**小さい順**に並ぶ
- 「Roles」に入れた役割がカード内のタグとして表示される

#### 入力項目

| CMS の項目 | 必須 | 説明 |
| :---- | :---- | :---- |
| Name | ○ | 氏名（英語表記） |
| Name (Japanese) | – | 日本語ページで使う氏名 |
| Role | – | 役職名（自由記述） |
| Role (Japanese) | – | 同上の日本語 |
| Team (Legacy) | – | 旧方式の所属。単一選択。今は「Roles」を推奨 |
| Roles (Multiple) | – | 役割を複数選択。カードにタグ表示 |
| Is Leader? | – | オンで Leadership セクションへ |
| Institution | – | 所属機関 |
| Institution (Japanese) | – | 同上の日本語 |
| Image | – | 顔写真。丸くトリミング表示 |
| Sort Order | – | 表示順（小さいほど先） |

#### 役割タグ一覧

ニュースのタグと違い、こちらは選択肢が決まっているので、CMS ではチェックボックスから選ぶだけです（自由入力できません）。全7種すべてに表示色が付いています。

**注意：カードに出る文字は、CMS のチェックボックスのラベルではなく内部の値です。** 例えば「Wiki & Video」にチェックを入れると、カードには `wiki-video` と表示されます。

| CMS の選択肢 | カードに出る文字 | 表示色 | 現在の使用数 |
| :---- | :---- | :---- | :---- |
| Wet Lab | `wet` | 青 | 1 |
| Dry Lab | `dry` | 緑 | 2 |
| Human Practice | `human practice` | 黄 | 1 |
| Funding | `funding` | ピンク | 0 |
| Wiki & Video | `wiki-video` | 紫 | 4 |
| Leader | `leader` | 赤 | 4 |
| Advisor | `advisor` | 藍 | 1 |

表示文字を「Wet Lab」のように整えたい場合は、コード側の修正が必要です。開発者に相談してください。

#### 「Team (Legacy)」について

旧方式の単一選択フィールドで、選択肢は Wet Lab / Dry Lab / Human Practice / Funding / Wiki & Video の5つ（Leader と Advisor はありません）。**「Roles」が入力されていればそちらが優先**され、「Roles」が空のときだけ「Team」の値が1つタグとして表示されます。

現在の23人の内訳：

| 状態 | 人数 | 表示されるタグ |
| :---- | :---- | :---- |
| 「Roles」のみ | 2 | 「Roles」の値 |
| 「Team」のみ | 7 | 「Team」の値1つ |
| 両方入力 | 10 | 「Roles」の値（「Team」は無視される） |
| どちらも未入力 | 4 | **タグなし** |

新しく追加するメンバーには「Roles (Multiple)」を使ってください。

#### 「Role」（役職名）との違い

「Role」は自由入力のテキストで、タグではなく肩書きとしてカードに表示されます。現在は「Team Leader」「Wiki team leader」「Funding team leader」「Human Practice team leader」「Frontend」（2人）「Researcher」「Presentation」「Mentor」「Corder」が使われています。（※「Corder」は「Coder」の誤記と思われます）

#### よくある作業

- **新メンバーが入った** → 新規作成
- **写真や役割が変わった** → 既存エントリを編集（新規作成ではない）
- **年度が変わってメンバー総入れ替え** → 旧メンバーを削除、新メンバーを追加
- **並び順を直したい** → 「Sort Order」の数値を振り直す（10, 20, 30… と間隔を空けておくと後で挿入しやすい）

### 6-3. Projects と年度切り替え

「Projects」は年度ごとのプロジェクト情報です。

#### 入力項目

| 項目 | 必須 |
| :---- | :---- |
| Year | ○ |
| Title / Title (Japanese) | Title のみ○ |
| Summary / Summary (Japanese) | Summary のみ○ |
| Description / Description (Japanese) | – |
| Wiki URL | – |
| Image | – |

- Summary … 短い紹介文（トップページなどに出る）
- Description … 長い本文（プロジェクト詳細ページ）

#### 年度を切り替える手順

トップページと /project ページには、「Global Settings」の「Current Project Year」で指定した年度のプロジェクトが表示されます。

**必ずこの順番で行ってください（例: 2027年に切り替える場合）**

1. **先に**「Projects」で「Year: 2027」のエントリを作成し、タイトル・概要を入力して Save
2. **その後**「Global Settings」の「Current Project Year」を「2027」に変更して Save

順番を逆にすると、指定した年度のプロジェクトがまだ存在しないため、/project ページはアーカイブページに転送されてしまいます。

これで自動的に：

- トップページと /project が2027年の内容になる
- 2026年は /archive 側に移動する（個別ページは /archive/2026）

現在の設定は **2026年度**です。

## 7. 画像の扱い

## 8. 日本語・英語の対応方法

**2つの方式が混在しています。**

### 方式A：1つのエントリに両言語のフィールド（ニュース以外すべて）

Activities / Sponsors / Projects / Team Members / Archive が該当。入力例：

| 項目 | 値 |
| :---- | :---- |
| Title | AI x Biology |
| Title (Japanese) | AI × 生物学 |

- 両方入力 → 言語切り替えで適切に表示される
- 英語のみ入力 → 日本語ページでも英語が表示される（フォールバック）
- **英語フィールドが必須**、日本語フィールドは任意

### 方式B：言語ごとに別記事（ニュースのみ）

News Articles (English) と News Articles (Japanese) で別々に作成します。片方だけ作ることも可能です（その言語のページにだけ出ます）。

## 9. Markdown 記法早見表

ニュース記事の「本文」欄で使える書き方です。Pages CMS のエディタはツールバーからも操作できますが、直接この記法を書いても同じ結果になります。

| やりたいこと | 書き方 | 結果 |
| :---- | :---- | :---- |
| 見出し（大） | `## 見出し` | 節の見出し |
| 見出し（小） | `### 小見出し` | その下の階層 |
| 太字 | `**強調**` | **強調** |
| 斜体 | `*強調*` | *強調* |
| 箇条書き | 行頭に `- ` | ・付きのリスト |
| 番号付きリスト | 行頭に `1. ` | 1. 2. 3. …（番号は自動で振り直される） |
| リンク | `[表示する文字](https://example.com)` | リンク |
| 画像 | `![説明](/media/ファイル名.jpg)` | 本文中の画像 |
| 引用 | 行頭に `> ` | 引用ブロック |
| 区切り線 | `---` を単独の行に | 横線 |
| 改行して段落を分ける | **空行を1行入れる** | 新しい段落 |

### 注意点

- **記事タイトルは「記事タイトル」欄が使われます。** 本文の先頭に `# タイトル` を書くと見出しが二重になるので、本文の見出しは `##` から始めてください
- **段落を分けるには空行が必要です。** 単に改行しただけでは同じ段落として続けて表示されます
- 本文中の画像は、まず「アイキャッチ画像」欄などのアップローダーで画像を追加し、生成された `/media/…` のパスを `![説明](/media/…)` の形で貼り付けてください（[7章](#7-画像の扱い)参照）
- 表（テーブル）や HTML の直接入力は、見た目が整わない場合があります。使う前に開発者に相談してください

## 10. 落とし穴と既知の問題

### 運用上の落とし穴

#### 1. 「公開日」を未来にしても予約投稿にはならない

日付による自動制御はありません。「公開する」がオンなら未来日付でも即座に公開され、一覧の先頭に来るだけです。下書きにしたい場合は「公開する」をオフにしてください。

#### 2. 「公開する」オフは「限定公開」ではない

オフにすると、そのページ自体が作られません。URL を知っていてもアクセスできない、完全な非公開です。

#### 3. Save = 即公開

CMS にステージング環境はありません。確認してから保存してください。

#### 4. 同じ言語の中でスラッグを重複させない

同じスラッグは使えないため、片方が失われます。EN/JA 間の重複は問題ありません。

#### 5. 保存しても反映されないフィールドがある

CMS のフォームに出ていても、サイト側が受け取らない項目があります（現状は Human Practice が該当）。下記Bを参照してください。

### 既知の不具合・要修正事項

#### A. PR プレビューが動作しない

README には PR ごとのプレビューが使えると書かれていますが、2026年8月に無効化されており、現在は動作しません。README の記述が古いままです。

#### B. Human Practice が機能していない（使わないこと）

CMS 上には「Human Practice」の入力メニューがありますが、**ここで編集・保存しても、サイトのどこにも反映されません。** 表示するページが存在しないためです。使わないでください。

さらに、**トップページの「Human Practice」カードはリンク切れ（404）になっています。** リンク先が存在しないページに転送される設定になったまま残っているためです。修正には開発者の作業が必要です。

#### C. 「/project/2026/」は年度切り替えに追随しない

このページだけは年度に固定されており、「Current Project Year」を 2027 に変えても 2026 のまま残ります。

#### D. CMS から編集できない項目がある

| 場所 | 編集できない項目 |
| :---- | :---- |
| Team Members | 経歴（bio） |
| Activities | 日付・詳細 |
| 支援ページ（/support, /ja/support） | 埋め込みの寄付案内PDF（ファイル自体がコードに直接指定されています） |

使う予定がある場合は開発者に相談してください。

## 12. 開発者向け：フィールドを追加するとき

コンテンツの構造を変えるときは、**必ず3か所をセットで更新**してください。

1. `src/content/config.ts` … Zod スキーマ（型と必須/任意の定義）
2. `.pages.yml` … CMS のフォーム定義
3. `src/pages/`, `src/components/` … 表示側の実装

抜けたときに何が起きるか：

| 更新したもの | 起きること |
| :---- | :---- |
| ①だけ | CMS のフォームに出ないので編集者が入力できない（→ [10章D](#d-cms-から編集できない項目がある) の状態） |
| ②だけ | 編集者は保存できるが、**値は読み捨てられ、どこにも反映されない**。ビルドは成功してしまうため気づきにくい（→ [10章B](#b-human-practice-が機能していない使わないこと) の状態） |
| ①②だけ | データは入るがどこにも表示されない |

> **補足：** Astro のコンテンツスキーマは既定で未知のフロントマター項目を黙って捨てます（`z.object` の strip 動作）。したがって `.pages.yml` にだけフィールドを足しても**ビルドは失敗しません**。エラーで気づけないぶん、③の実装漏れに注意してください。
> 実際、ニュースの `slug` と `body` は `.pages.yml` にありますが `config.ts` にはありません（`slug` はファイル名として使われるため、これは意図的な設計です）。

変更後は必ず `npm run build` を実行し、既存コンテンツがスキーマ違反にならないか確認してください。必須項目を追加する場合は、既存の全ファイルにその項目を追記する必要があります（既存データを壊さないため、原則 `.optional()` か `.default()` を付けるのが安全です）。

その他の開発方針は以下を参照：

- `docs/ai/architecture.md`
- `docs/ai/coding-rules.md`
- `docs/ai/content-rules.md`
- `AGENTS.md`
